## 1. Условие и цель

Разработать консольную имитационную программу на языке C для Linux, в которой взаимодействие читателей и писателей организовано по протоколу TCP в архитектуре клиент–сервер. Предметная модель сохранена: база данных — отсортированный массив положительных целых чисел; читатели получают только подтверждённую версию; писатели подготавливают следующую версию по стадиям и публикуют её после проверки.

Участники подключаются к серверу по IP-адресу и TCP-порту. Клиенты могут работать на одном компьютере или на разных компьютерах сети.

## 2. Модель и инварианты

Сервер хранит два буфера базы, индекс активного буфера и номер подтверждённой версии. Читатель запрашивает запись по индексу; ответ содержит номер версии, индекс, значение, порядковый номер записи и произведение значения на номер записи.

Писатель начинает подготовку следующей версии, затем последовательно сообщает серверу о завершении стадий. Сервер изменяет неактивный буфер, сортирует его и проверяет перед публикацией.

Инварианты:
1. Одновременно новую версию подготавливает не более одного писателя.
2. Читатель не получает промежуточные данные.
3. Рабочая копия отделена от подтверждённой версии.
4. Публикация возможна только после выполнения всех стадий и проверки массива.
5. Номер версии увеличивается только после успешной публикации.
6. При отмене подготовки или потере соединения писателя последняя подтверждённая версия сохраняется.

Стратегии чтения:
- `READ_OLD` — во время подготовки читатель получает предыдущую подтверждённую версию.
- `WAIT_NEW` — запрос читателя ожидает публикации или отмены подготовки.

## 3. Архитектура

### 3.1. Сервер

Сервер создаёт TCP-сокет, привязывает его к указанному адресу и порту и принимает соединения. Для обслуживания нескольких клиентов используется `poll()`: сервер обрабатывает новые подключения и поступающие команды в одном цикле событий.

Сервер является единственным владельцем базы и состояния публикации. Последовательная обработка команд исключает одновременное изменение состояния несколькими обработчиками.

### 3.2. Клиенты

- **Читатель** подключается к серверу и отправляет запросы чтения.
- **Писатель** отправляет команды начала подготовки, стадий, публикации или отмены.
- **Наблюдатель** запрашивает агрегированное состояние сервера и отображает номер версии, размер базы, состояние подготовки и статистику.

Каждый клиент запускается отдельным процессом. Несколько клиентов могут одновременно подключаться к одному серверу.

### 3.3. Протокол

Прикладной протокол текстовый, построчный: каждая команда и ответ завершается символом новой строки.

| Команда | Назначение |
|---|---|
| `HELLO id` | регистрация клиента |
| `READ index` | чтение записи |
| `BEGIN seed` | начало подготовки версии |
| `STAGE number` | завершение стадии |
| `PUBLISH` | проверка и публикация |
| `ABORT` | отмена подготовки |
| `STATUS` | получение сводки состояния |
| `QUIT` | завершение клиента |

## 4. Интерфейс и запуск

Сборка:

```sh
make
```

Запуск сервера:

```sh
./bin/idz4 server --bind 0.0.0.0 --port 5050 --strategy READ_OLD
```

Запуск клиентов:

```sh
./bin/idz4 reader --host 127.0.0.1 --port 5050 --id 1 --ops 5
./bin/idz4 writer --host 127.0.0.1 --port 5050 --id 2 --ops 2 --seed 42
./bin/idz4 observer --host 127.0.0.1 --port 5050 --id 90 --ops 0
```

Для распределённого запуска вместо loopback-адреса указывается адрес компьютера с сервером. Серверные параметры: адрес, порт, стратегия чтения, число операций, число стадий и размер базы. Клиентские параметры: адрес сервера, порт, идентификатор, число операций и начальное значение генератора.

## 5. Наблюдаемые события и завершение

Сервер отображает подключения, начало подготовки, завершение стадий, чтения, ожидание публикации, успешную публикацию и отмену версии. Клиенты отображают ответы сервера. Наблюдатель получает сводную информацию по TCP-запросу `STATUS`.

Клиенты завершаются после заданного количества операций или по Ctrl+C. Сервер завершает работу по Ctrl+C или SIGTERM. Незавершённая подготовка отменяется, ожидающие читатели получают последнюю подтверждённую версию, после чего сервер закрывает соединения. Журнал и итоговые счётчики сохраняются в `logs/idz4_server.log`.

## 6. Проверка

Команда `make test` собирает программу и запускает интеграционные сценарии. Проверяются чтение и публикация при `READ_OLD`, получение сводки наблюдателем, а также ожидание читателя до публикации при `WAIT_NEW`.
