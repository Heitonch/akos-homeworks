## 1. Условие и цель

Разработать консольную программу на языке C для Linux, моделирующую чтение подтверждённых данных в клиент-серверной архитектуре с обменом по TCP. База данных представлена отсортированным массивом положительных целых чисел и номером подтверждённой версии.

Читатель случайным образом выбирает запись и выводит её индекс, значение и произведение значения на порядковый номер записи. Писатель формирует новую версию в несколько стадий. До подтверждения новой версии читатели либо продолжают читать предыдущую подтверждённую версию, либо ожидают завершения подготовки — в зависимости от выбранной стратегии. После полного формирования сервер проверяет массив и атомарно публикует новую версию. Одновременно формировать изменения может только один писатель.

Каждый читатель и писатель является самостоятельным участником модели и запускается отдельным процессом. Сервер и клиенты могут работать на одном компьютере или на разных компьютерах сети. Адрес сервера и TCP-порт задаются аргументами командной строки.

## 2. Модель данных и правила работы

Сервер хранит два буфера массива, индекс активного буфера и номер подтверждённой версии. Начальная версия имеет номер 1. При успешной публикации номер увеличивается на единицу.

Читатель выбирает индекс записи с помощью воспроизводимого псевдослучайного генератора. Начальное состояние генератора определяется параметрами `--seed` и `--id`. Поэтому при одинаковых параметрах последовательность выбранных индексов повторяется. В ответ читатель получает номер версии, индекс, значение, порядковый номер записи (нумерация с единицы) и произведение значения на порядковый номер записи.

Писатель начинает подготовку следующей версии, после чего последовательно сообщает серверу о завершении стадий. Значения изменяются в неактивном буфере. После последней стадии сервер сортирует массив и проверяет, что все элементы находятся в заданном диапазоне, а порядок элементов не убывает. Только после успешной проверки новый буфер становится активным.

Соблюдаются следующие инварианты:

1. Одновременно новую версию подготавливает не более одного писателя.
2. Читатель не получает промежуточные данные.
3. Подтверждённый буфер не изменяется во время подготовки.
4. Публикация выполняется только после всех стадий и проверки массива.
5. Номер версии увеличивается только после публикации.
6. При отмене подготовки или потере соединения писателя последняя подтверждённая версия сохраняется.

Используются две стратегии чтения:

- `READ_OLD` — во время подготовки читатели получают предыдущую подтверждённую версию;
- `WAIT_NEW` — запросы читателей ожидают публикации или отмены подготовки.

## 3. Структура программы

Программа разделена на модули по назначению.

| Файл | Ответственность |
|---|---|
| `main.c` | выбор роли процесса и разбор аргументов клиента |
| `server.c` | состояние базы, TCP-сервер, обработка команд и публикация версий |
| `client.c` | общие функции клиента, подключение, сигналы и задержки |
| `protocol.c` | отправка и приём строк протокола, проверка числовых значений и подключение к серверу |
| `reader.c` | цикл запросов чтения |
| `writer.c` | цикл подготовки, отправки стадий и публикации |
| `observer.c` | получение и вывод состояния сервера |
| `common.h`, `client_internal.h` | общие объявления и интерфейсы модулей |

Сервер обслуживает подключения с помощью `poll()`. Состояние базы изменяется последовательно в одном цикле обработки событий. Для каждого клиента сервер хранит файловый дескриптор, роль, идентификатор и буфер приёма. Незавершённые строки TCP накапливаются до символа новой строки. Задержка чтения выполняется на стороне читателя перед отправкой запроса, а задержки подготовки и подтверждения — на стороне писателя. Благодаря этому искусственные задержки не блокируют цикл обслуживания остальных клиентов.

Клиенты являются отдельными процессами. Каждый устанавливает TCP-соединение, регистрирует роль командой `HELLO` и выполняет операции в соответствии со своей ролью.

## 4. Протокол обмена

Протокол текстовый, построчный. Каждая команда и каждый ответ завершаются символом новой строки.

| Команда | Назначение |
|---|---|
| `HELLO role id` | регистрация клиента |
| `READ index` | чтение записи |
| `BEGIN seed` | начало подготовки версии |
| `STAGE number` | завершение очередной стадии |
| `PUBLISH` | проверка и публикация версии |
| `ABORT` | отмена подготовки |
| `STATUS` | получение состояния сервера наблюдателем |
| `QUIT` | штатное завершение клиента |

Отправка сообщений учитывает возможность частичной передачи данных через TCP. Сервер также принимает команды, которые могут поступать несколькими фрагментами. Числовые аргументы проверяются на допустимый диапазон и отсутствие лишних символов.

## 5. Пользовательский интерфейс и запуск

Сборка выполняется командой:

```sh
make
```

Запуск сервера:

```sh
./bin/idz4 server --bind 0.0.0.0 --port 5050 --strategy READ_OLD
```

Запуск клиентов в отдельных терминалах:

```sh
./bin/idz4 reader --host 127.0.0.1 --port 5050 --id 1 --ops 5
./bin/idz4 writer --host 127.0.0.1 --port 5050 --id 2 --ops 2 --seed 42
./bin/idz4 observer --host 127.0.0.1 --port 5050 --id 90 --ops 0
```

Для распределённого запуска в `--host` указывается IPv4-адрес компьютера с сервером. Параметры сервера позволяют выбрать адрес и порт, стратегию чтения, размер массива, число стадий, диапазон значений, начальное значение генератора и задержки. Клиентские параметры задают адрес сервера, порт, идентификатор, число операций и seed.

Если `--ops` клиента не задан, используется значение `--ops` сервера. Значение `--ops 0` означает неограниченное число операций до сигнала остановки.

## 6. Наблюдаемые события и завершение

В консоль сервера выводятся подключения клиентов, начало подготовки, завершение стадий, результаты чтения, ожидание публикации, публикация и отмена версии. Клиенты отображают полученные ответы. Наблюдатель периодически выводит номер версии, состояние записи и статистику.

Клиент завершается после заданного количества операций или по `Ctrl+C`/`SIGTERM`. Сервер завершается по `Ctrl+C`/`SIGTERM`. При остановке сервера незавершённая подготовка отменяется, ожидающие читатели получают последнюю подтверждённую версию, после чего соединения закрываются.

События и итоговые счётчики записываются в `logs/idz4_server.log`.

## 7. Тестирование

Автоматические проверки запускаются командой:

```sh
make test
```

Интеграционные сценарии проверяют:

- чтение предыдущей версии во время подготовки при `READ_OLD`;
- ожидание публикации и получение новой версии при `WAIT_NEW`;
- получение состояния сервера наблюдателем;
- публикацию массива из одного элемента с одной стадией;
- отклонение некорректного порта и числа стадий;
- отклонение некорректного порта клиента;
- воспроизводимость псевдослучайной последовательности индексов читателя при одинаковых `--seed` и `--id`;
- отклонение некорректной регистрации и команд с лишними символами;
- запрет одновременной подготовки версии двумя писателями;
- освобождение блокировки и сохранение подтверждённой версии при отключении писателя;
- работу нескольких наблюдателей и корректное закрытие соединений по `QUIT`.

Отдельные проверки TCP-протокола проверяют отклонение отрицательной стадии, лишних символов в числовых командах и возврат ожидающих читателей к последней подтверждённой версии после отмены подготовки.

Сборка выполняется с флагами `-Wall -Wextra -Wpedantic -Werror`. Дополнительно интеграционные сценарии запускались со средствами AddressSanitizer и UndefinedBehaviorSanitizer. В проверенных сценариях ошибок памяти и неопределённого поведения не обнаружено.

## 8. Вывод

В ИДЗ 4 предметная модель читателей и писателей перенесена в клиент-серверную архитектуру с обменом по TCP. Сервер централизованно хранит подтверждённую базу и управляет публикацией новых версий. Клиенты-читатели, писатели и наблюдатели могут запускаться независимо и подключаться к серверу по сетевому адресу и порту.

Сохранены правила подтверждённого чтения, поэтапной подготовки, проверки и публикации версии. Реализованы случайный воспроизводимый выбор записей, две стратегии чтения, исключительная блокировка писателя, обработка потери соединения писателя, проверка входных команд, прерываемое ожидание ответов, штатное завершение клиентов, журналирование и автоматические тесты.
