## 1. Условие задания

Требуется разработать консольную программу на языке C для Linux, моделирующую работу читателей и писателей с базой данных.

База данных представляет собой отсортированный массив положительных целых чисел. У каждой опубликованной версии есть номер. Читатель выбирает случайную запись из подтверждённой версии и выводит её индекс, значение, порядковый номер записи и произведение значения на номер записи.

Писатель готовит новую версию базы в несколько стадий. Пока подготовка не закончена, читатели не должны получать доступ к промежуточным данным. После завершения подготовки новая версия проверяется и только после успешной проверки становится текущей подтверждённой версией.

В задании используются два режима чтения:

- `READ_OLD` — во время подготовки читатели продолжают обращаться к последней подтверждённой версии;
- `WAIT_NEW` — если писатель уже готовит новую версию, читатель ожидает её публикации.

В ИДЗ 3 предметная область и основные правила из предыдущих заданий сохранены. Изменён способ организации участников: теперь читатели и писатели представлены отдельными процессами.

## 2. Общая модель

В программе используются две роли:

- **читатель** — выполняет заданное количество операций чтения или работает до получения команды остановки;
- **писатель** — создаёт новую версию, изменяет её по стадиям, проверяет и публикует.

Размер базы, начальные значения, количество операций, диапазон новых значений, число стадий, стратегия чтения, задержки и начальное значение генератора задаются пользователем или конфигурационным файлом. В реализациях с родительским процессом поля `readers` и `writers` определяют число дочерних процессов. В независимых реализациях участники запускаются вручную, поэтому их фактическое число определяется количеством запущенных экземпляров. Для независимого варианта с разделяемой памятью значение `writers` должно соответствовать числу запущенных писателей: оно используется при пробуждении писателей во время общей остановки.

Начальная версия базы имеет номер 1. При успешной публикации номер увеличивается на единицу.

### 2.1. Инварианты

Во всех четырёх реализациях соблюдаются следующие правила:

1. Одновременно новую версию готовит только один писатель.
2. Читатель получает данные только из подтверждённого буфера.
3. Писатель изменяет отдельную рабочую копию, не затрагивая текущую подтверждённую версию.
4. Перед публикацией рабочий массив сортируется и проверяется: все значения должны быть положительными, порядок — неубывающим.
5. Номер версии увеличивается только после успешной проверки и публикации.
6. Если подготовка прервана, рабочая копия отбрасывается, а последняя подтверждённая версия остаётся активной.

## 3. Организация процессов

Для выполнения требований реализованы четыре программы с одной предметной логикой и разными способами взаимодействия.

### 3.1. Родительский процесс и именованные семафоры

Исполняемый файл: `bin/parent_named`.

Родительский процесс считывает конфигурацию, создаёт объект POSIX shared memory, инициализирует именованные POSIX-семафоры и запускает дочерние процессы с помощью `fork()`.

Для каждого читателя и каждого писателя создаётся отдельный процесс. После запуска участники самостоятельно выполняют свои операции и завершаются по достижении заданного числа действий или после запроса остановки.

Используются:

- `shm_open`, `ftruncate`, `mmap` — создание и подключение разделяемой памяти;
- `sem_open`, `sem_wait`, `sem_post` — синхронизация;
- `fork`, `waitpid` — создание и сбор дочерних процессов.

В разделяемой памяти находятся параметры модели, номер версии, состояние публикации, статистика и два буфера базы. Имена семафоров создаются с уникальным префиксом, содержащим PID родительского процесса.

### 3.2. Родительский процесс и неименованные семафоры

Исполняемый файл: `bin/parent_unnamed`.

Схема запуска участников такая же, как в предыдущем варианте. Отличается размещение семафоров: они находятся непосредственно в структуре разделяемой памяти и создаются вызовом `sem_init` с параметром `pshared = 1`.

Таким образом, синхронизация выполняется неименованными POSIX-семафорами, доступными всем процессам, отображающим один и тот же участок памяти.

### 3.3. Независимые процессы и разделяемая память

Для этого варианта подготовлены отдельные исполняемые файлы:

- `bin/shm_init` — создание сеанса и инициализация базы;
- `bin/shm_reader` — независимый процесс-читатель;
- `bin/shm_writer` — независимый процесс-писатель;
- `bin/shm_status` — просмотр состояния и статистики;
- `bin/shm_stop` — запрос остановки;
- `bin/shm_cleanup` — удаление IPC-ресурсов.

Сначала запускается `shm_init`. Он создаёт POSIX shared memory и именованные семафоры, записывает начальную версию базы и завершает работу. После этого читатели и писатели могут запускаться независимо друг от друга, в том числе из разных терминалов.

Все процессы подключаются к одному сеансу по известному имени разделяемой памяти и открывают созданные именованные семафоры. Для нескольких процессов одной роли используются разные идентификаторы `--id`. Число запущенных процессов задаётся командами в терминалах, а не автоматически полями `readers` и `writers`; при этом значение `writers` в конфигурации должно совпадать с числом запущенных писателей для корректного пробуждения при остановке.

### 3.4. Независимые процессы и очередь сообщений

В последнем варианте база находится в процессе-сервере. Обмен между сервером и независимыми клиентами выполняется через POSIX message queues.

Исполняемые файлы:

- `bin/mq_server` — сервер базы данных;
- `bin/mq_reader` — клиент-читатель;
- `bin/mq_writer` — клиент-писатель;
- `bin/mq_stop` — команда остановки сервера;
- `bin/mq_cleanup` — удаление очереди и именованных семафоров.

Сервер создаёт общую очередь запросов. Каждый клиент дополнительно создаёт собственную очередь ответов и передаёт её имя серверу. Благодаря этому ответы одного клиента не забираются другим процессом. Читатели и писатели запускаются вручную; их фактическое число определяется количеством запущенных клиентов.

Читатель отправляет запрос на чтение и получает номер версии, индекс, значение и произведение. Писатель отправляет сообщения о начале подготовки, завершении каждой стадии и публикации. Между стадиями сервер продолжает принимать запросы читателей.

Для синхронизации используются именованные POSIX-семафоры:

- семафор писателей не позволяет двум писателям одновременно готовить версии;
- семафор состояния защищает операции с текущей версией на стороне сервера;
- семафор журнала обеспечивает последовательную запись событий.

При стратегии `WAIT_NEW` сервер сохраняет запросы читателей в списке ожидающих и отвечает на них после публикации новой версии или отмены подготовки. При `READ_OLD` сервер сразу возвращает данные из активного буфера.

## 4. Подготовка и публикация версии

В реализациях с разделяемой памятью используется двойная буферизация. Один буфер содержит подтверждённую версию, второй предназначен для подготовки следующей.

Писатель получает право на запись, копирует активный буфер в неактивный и устанавливает признак подготовки. Затем он заменяет значения на нескольких стадиях. Границы стадий вычисляются с использованием 64-битной арифметики, чтобы избежать переполнения при больших размерах базы и количестве стадий.

После последней стадии рабочий массив сортируется и проверяется. Если проверка прошла успешно, под защитой семафора переключается индекс активного буфера и увеличивается номер версии. Если подготовка прервана, активный буфер не меняется.

В реализации с очередью сообщений те же действия выполняет сервер по запросам писателя. Рабочая копия хранится отдельно от активной базы. Публикация выполняется только после получения всех стадий и успешной проверки.

## 5. Пользовательский интерфейс и параметры

Первые две программы могут запрашивать параметры интерактивно. Для автоматических запусков предусмотрен конфигурационный файл формата `key=value`.

Пример:

```text
size=5
initial=2,5,8,12,19
readers=2
writers=1
ops=2
min=1
max=20
stages=3
strategy=READ_OLD
read_ms=0
prep_ms=10
confirm_ms=0
seed=42
```

Параметры:

| Поле | Назначение |
|---|---|
| `size` | размер базы |
| `initial` | начальный отсортированный массив |
| `readers` | количество читателей |
| `writers` | количество писателей |
| `ops` | количество операций каждого участника; `0` — без ограничения |
| `min`, `max` | диапазон новых значений |
| `stages` | количество стадий подготовки |
| `strategy` | `READ_OLD` или `WAIT_NEW` |
| `read_ms` | задержка после чтения |
| `prep_ms` | задержка после стадии подготовки |
| `confirm_ms` | задержка перед подтверждением |
| `seed` | начальное значение генератора случайных чисел |

Дополнительно поддерживаются аргументы командной строки для выбора конфигурации и переопределения основных параметров.

Во время работы выводятся начало работы участников, чтения, начало подготовки, завершение стадий, проверка, публикация и отмена версии. В вариантах с разделяемой памятью для больших массивов в сообщениях показывается только начало базы и общее число элементов. В варианте с очередью сообщений сервер не печатает массив целиком: в журнале остаются результаты чтений и итоговая статистика.

## 6. Завершение и обработка сигналов

Во всех вариантах предусмотрено завершение по достижении конечного числа операций и остановка по сигналу.

Обработчики `SIGINT` и `SIGTERM` не выполняют очистку IPC напрямую. Они только устанавливают флаг прерывания. Освобождение ресурсов выполняется обычным кодом программы.

В первых двух вариантах родительский процесс отслеживает завершение потомков через `waitpid`. При Ctrl+C он устанавливает общий признак остановки, будит ожидающих читателей и писателей и дожидается завершения дочерних процессов.

В независимом варианте с разделяемой памятью остановка может быть запрошена командой `shm_stop`. Команда `shm_cleanup` сначала просит участников завершиться и проверяет счётчик активных процессов. Если участники ещё работают, обычная очистка не удаляет ресурсы. Для восстановления после аварийного уничтожения процесса предусмотрен отдельный принудительный режим `--force`.

В варианте с очередью сообщений сервер можно остановить командой `mq_stop` или Ctrl+C. При завершении сервер отменяет незавершённую подготовку и отвечает ожидающим читателям данными последней подтверждённой версии. Клиенты обнаруживают завершение сервера и завершаются. После остановки сервера команда `mq_cleanup` удаляет оставшиеся именованные семафоры.

## 7. Ввод-вывод и журналирование

Для консольного ввода и вывода используются файловые дескрипторы и функции `read`, `write`, `open`, `close`, `dprintf`. Журналы открываются в режиме добавления (`O_APPEND`).

В журнал записываются:

- запуск и завершение моделирования;
- результаты операций чтения;
- запуск и завершение участников в родительских реализациях и независимом варианте с разделяемой памятью; в варианте MQ подключение и завершение клиента выводятся в его консоль, а отдельная запись о завершении в журнал сервера не добавляется;
- начало подготовки новой версии;
- завершение каждой стадии;
- результат проверки;
- публикация или отмена версии;
- итоговая статистика.

Файлы журналов сохраняются в каталоге `logs/`. Для общей записи из нескольких процессов доступ к журналу защищается семафором.

## 8. Дополнительные возможности

В проект добавлены функции, выходящие за рамки базовой модели:

1. **Конфигурационные файлы и аргументы командной строки.** Один набор параметров можно повторно использовать для всех запусков.
2. **Воспроизводимый seed.** При фиксированном начальном значении генератора последовательность случайных значений каждого участника повторяется. Порядок выполнения процессов по-прежнему определяется планировщиком ОС.
3. **Настраиваемые задержки.** Можно замедлить чтение, стадии подготовки и подтверждение, чтобы наблюдать взаимодействие процессов.
4. **Итоговая статистика.** Считаются чтения, публикации, завершённые стадии и отменённые публикации.
5. **Безопасная отмена незавершённой версии.** При прерывании рабочая копия не становится активной; подтверждённая версия сохраняется.
6. **Просмотр состояния независимого сеанса.** Команда `shm_status` показывает текущую версию, признак подготовки, количество активных процессов и статистику.

## 10. Вывод

В результате реализованы четыре варианта программы для моделирования читателей и писателей с использованием взаимодействующих процессов.

В первых двух вариантах процессы создаются единым родителем и используют соответственно именованные и неименованные POSIX-семафоры вместе с POSIX shared memory. В третьем варианте читатели и писатели запускаются независимо и взаимодействуют через разделяемую память и именованные семафоры. В четвёртом варианте независимые клиенты обмениваются запросами и ответами с сервером через POSIX message queues, а именованные семафоры обеспечивают синхронизацию.

Во всех вариантах сохранены правила чтения подтверждённых данных, поэтапной подготовки новой версии, проверки и атомарной публикации. Реализованы обработка сигналов, очистка IPC-ресурсов, журналирование, тестовые конфигурации и автоматические проверки.
